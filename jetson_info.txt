Here are the issues in simple, precise points:

1️⃣ Why 6-hour offline replay happens
    • You have 1 TensorRT engine
    • GPU can process only one inference at a time
    • 5 cameras compete for it
    • Effective throughput = 1 / inference_time
    • With ~180ms per inference → ~5.5 FPS total
    • 120k frames ÷ 5.5 FPS ≈ 6 hours
It’s not a bug. It’s math.

2️⃣ Why INFER_LOCK caused slowdown
    • All camera threads try to infer simultaneously
    • Lock forces strict serialization
    • Threads context-switch constantly
    • CPU overhead increases
    • GPU sits idle between thread switches
Result: lower effective throughput.

3️⃣ Why your first queue-based pipeline still didn’t help much
    • Each camera pushes frame
    • Immediately blocks waiting for result
    • So behavior is still serialized
    • Added queue + polling overhead
    • No real parallelism gained
You changed structure, not physics.

4️⃣ Why MAXN gave over-current warning
    • GPU tried to draw higher power
    • Your adapter/carrier board limited current
    • Firmware throttled clocks
    • Performance capped artificially
That’s power limitation, not software.

5️⃣ Why backend is NOT the bottleneck
    • Event sending is async
    • Inference happens before event creation
    • Inference time >> HTTP time
    • So GPU dominates runtime

6️⃣ Core Reality
Your system throughput is bounded by:
Total FPS = 1 / inference_time
If inference = 40ms → max 25 FPS total
If inference = 180ms → max 5.5 FPS total
With 5 cameras:
Divide that across cameras.

7️⃣ What Actually Controls Performance
Only these matter:
    • Resolution (640 vs 512)
    • TensorRT vs PyTorch
    • Power mode (15W vs MAXN)
    • Number of cameras
    • Processing FPS
Threading tricks don’t change GPU physics.

    status = "ON_TIME"    # Within tolerance

Actual start 08:55 → offset = -5 min → ON_TIME (-5 to +10)
Actual start 09:05 → offset = +5 min → ON_TIME (-5 to +10)
Actual start 09:15 → offset = +15 min → LATE (> +10)
