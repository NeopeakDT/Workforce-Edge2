─────────────────────────────────────────────────────────────────────────────
STEP 1: JETSON DETECTS ACTIVITY (edge_detector.py)
─────────────────────────────────────────────────────────────────────────────

WHERE: Jetson device (on-farm)
WHAT: Runs YOLO model on video frames continuously
OUTPUT: Events via HTTP POST to backend

STATE MACHINE:
    INACTIVE → START_CANDIDATE (detected) → FRAME_AGGREGATE (every 10 sec)
    → END_CANDIDATE (stopped) → INACTIVE

EXAMPLE EVENT:
{
  "event_id": "abc-123",
  "session_id": "session-xyz",
  "event_type": "START_CANDIDATE",
  "activity_type": "FEEDING",
  "confidence": 0.92,
  "event_time": "2026-02-14T10:30:00Z"
}

─────────────────────────────────────────────────────────────────────────────
STEP 2: BACKEND RECEIVES EVENT (event_ingest_api.py)
─────────────────────────────────────────────────────────────────────────────

ENDPOINT: POST /api/v1/ingest/event
VALIDATES:
  ✅ X-DEVICE-KEY authentication
  ✅ UTC timestamp
  ✅ Confidence (0-1 range)
  ✅ Activity type exists
  ✅ Device registered

DATABASE: Inserts into activity_detection_event (APPEND-ONLY LOG)
  • event_id, session_id, event_type, event_time
  • farm_id, camera_id, activity_type_id
  • ai_confidence, payload
  ⚠️  activity_instance_id = NULL (will be filled by aggregator)

IMPORTANT: This table is immutable (never update after insert)

─────────────────────────────────────────────────────────────────────────────
STEP 3: AGGREGATOR CREATES INSTANCES (activity_aggregator.py)
─────────────────────────────────────────────────────────────────────────────

TRIGGER: run_phase5.py (orchestrator)
READS: activity_detection_event WHERE activity_instance_id IS NULL

MERGE_GAP_CONFIGURATION (different by activity type):
  MILKING: 3 minutes
  FEEDING: 5 minutes
  SCRAPPING: 12 minutes

FOR START_CANDIDATE:
  1. Resolve zone_id from camera_activity_zone table
  2. Check: Is active instance already running?
     - YES → Reuse it (don't create new)
     - NO → Go to step 3
  3. Check: Should we MERGE with recently ended?
     - If ended within merge gap → Resume it
     - Otherwise → Create new instance
  4. Link event to instance
  
OUTPUT: activity_instance (status = IN_PROGRESS, not finalized yet!)
  • actual_start_at (UTC)
  • actual_end_at (NULL initially)
  • zone_id, activity_type_id, farm_id

FOR FRAME_AGGREGATE:
  • Find active instance
  • Update last_seen_at = event_time (heartbeat)
  • Link event

FOR END_CANDIDATE:
  • Find active instance
  • Compute duration = event_time - actual_start_at
  • Set actual_end_at and actual_duration_sec
  • Link event
  ⚠️  Status still = IN_PROGRESS (resolved in STEP-4!)

⚠️  CRITICAL: Status remains IN_PROGRESS after aggregator!

─────────────────────────────────────────────────────────────────────────────
STEP 4: RESOLVER FINALIZES STATUS ⭐ (activity_schedule_resolver.py)
─────────────────────────────────────────────────────────────────────────────

⭐ THIS WAS COMPLETELY MISSING FROM OLD DOCUMENTATION!

TRIGGER: run_phase5.py (runs AFTER aggregator in STEP-3)
READS: activity_instance WHERE actual_end_at IS NOT NULL
                             AND status = 'IN_PROGRESS'

DURATION VALIDATION:
  MAX_ACTIVITY_DURATION_SEC = 3 hours (10,800 seconds)
  If duration > 3 hours → Mark as LATE (anomaly case)

TIMEZONE STRATEGY:
  • All events are UTC (canonical time)
  • Schedule times are farm LOCAL timezone
  • Resolver converts both to UTC for offset computation
  • Handles cross-midnight schedules (10 PM - 2 AM)

SCHEDULE MATCHING ALGORITHM:
  1. Get all active schedules for (farm, activity_type)
  2. For EACH schedule:
     a) Build ideal window in farm LOCAL time
        - ideal_start_local = farm_tz.localize(datetime.combine(date, start_time))
        - ideal_end_local = farm_tz.localize(datetime.combine(date, end_time))
        - If end < start → add 1 day (cross-midnight)
     b) Convert ideal window to UTC (canonical)
     c) Compute offsets in minutes:
        - started_offset = (actual_start_utc - ideal_start_utc) / 60
        - ended_offset = (actual_end_utc - ideal_end_utc) / 60
     d) Compute score (lower = better match):
        score = abs(started_offset) + (0.3 * abs(ended_offset))
        (Start time weighted 3x more important than end)
  3. Select schedule with minimum score (best match)

STATUS FINALIZATION:
  IF started_offset < -(tolerance_early_min):
      status = 'EARLY'    (started too early)
  ELIF started_offset > tolerance_late_min:
      status = 'LATE'     (started too late)
  ELSE:
      status = 'ON_TIME'  (within tolerance)

OUTPUT: Updates activity_instance with:
  • status = 'EARLY' | 'ON_TIME' | 'LATE' (FINALIZED!)
  • activity_schedule_id (now bound to schedule)
  • started_offset_min (how many minutes before/after ideal)
  • ended_offset_min (when activity ended vs ideal)

⭐ STATUS IS FINALIZED HERE, NOT IN CRON JOB!

EXAMPLE:
  Activity started at 10:30 UTC
  Schedule ideal start: 10:00 UTC
  Tolerance late: 5 minutes
  
  started_offset = (10:30 - 10:00) / 60 = +30 minutes
  → 30 > 5 (tolerance) → status = 'LATE'
  → Record: started 30 minutes late

─────────────────────────────────────────────────────────────────────────────
STEP 5: MISSED ACTIVITY CRON (missed_activity_cron.py)
─────────────────────────────────────────────────────────────────────────────

TRIGGER: Nightly cron (after phases 3-4 complete)
CURRENTLY: ⚠️ DISABLED (can be re-enabled by removing markers)

FOR EACH ACTIVE SCHEDULE:
  1. Compute late cutoff = ideal_end + tolerance_late (in farm LOCAL time)
  2. If current time <= cutoff → SKIP (window still open)
  3. If current time > cutoff → Check if instance exists
  4. If NOT exists → Create MISSED instance

OUTPUT: activity_instance with:
  • status = 'MISSED'
  • source = 'SYSTEM' (not 'AI')
  • activity_schedule_id (linked to schedule)

PURPOSE: Record scheduled activities that weren't detected

📦 DATABASE TABLES
================================================================================

TABLE: activity_detection_event (APPEND-ONLY LOG)
────────────────────────────────────────────────────────────────────────────
Columns:
  • event_id: Unique ID from Jetson
  • session_id: Jetson session
  • event_type: START_CANDIDATE | FRAME_AGGREGATE | END_CANDIDATE
  • event_time: When activity occurred (UTC)
  • ai_confidence: 0.0 to 1.0
  • farm_id, camera_id, activity_type_id: IDs
  • activity_instance_id: ← Links to instance (NULL → aggregator → resolver)
  • payload: JSON with objects, zones, metadata
  • created_at: When backend received it

LIFECYCLE: activity_instance_id = NULL
               ↓ (aggregator processes)
           activity_instance_id = 123
               ↓ (ready for reporting)

⚠️  NEVER UPDATE after insert (immutable audit log)


TABLE: activity_instance (SINGLE SOURCE OF TRUTH)
────────────────────────────────────────────────────────────────────────────
Columns:
  • id: Unique instance ID
  • farm_id, zone_id, activity_type_id: Which farm/zone/activity
  • activity_date: Date in farm timezone (for grouping)
  • activity_schedule_id: ← Links to schedule (set by resolver)
  
  • actual_start_at: When activity started (UTC, set by aggregator)
  • actual_end_at: When activity ended (UTC, set by aggregator)
  • actual_duration_sec: Duration in seconds (set by aggregator)
  
  • status: IN_PROGRESS → EARLY/ON_TIME/LATE/MISSED (finalized by resolver)
  • started_offset_min: Minutes early/late vs schedule (set by resolver)
  • ended_offset_min: Activity end offset vs ideal (set by resolver)
  
  • source: 'AI' (detector) | 'MANUAL' (user created) | 'SYSTEM' (MISSED)
  • created_at, updated_at: Timestamps

STATUS LIFECYCLE EXPLAINED:
  NULL (event log only)
    ↓
  IN_PROGRESS (aggregator creates in STEP-3)
    ↓
  EARLY / ON_TIME / LATE (resolver finalizes in STEP-4)
    OR
  MISSED (cron creates in STEP-5, when enabled)

🎯 KEY CONCEPTS YOU MUST UNDERSTAND
================================================================================

1. EXECUTION ORDER IS CRITICAL:
   ✅ DO: aggregator (STEP-3) → resolver (STEP-4) → cron (STEP-5)
   ❌ DON'T: Run in any other order
   
   Why? Resolver needs ended instances from aggregator
        Cron needs resolved instances from resolver

2. WHERE STATUS IS FINALIZED:
   ✅ STEP-4 (Resolver) - This is the authoritative place
   ❌ NOT in STEP-5 (Cron)
   ❌ NOT in aggregator (leaves IN_PROGRESS on purpose)

3. STATUS VALUES:
   Valid: IN_PROGRESS, EARLY, ON_TIME, LATE, MISSED
   Invalid: COMPLETED (doesn't exist!)
   
4. TIMEZONE HANDLING:
   • Use UTC for all calculations (canonical)
   • Display times in farm LOCAL timezone
   • Offsets always computed in UTC
   • Cross-midnight schedules handled automatically

5. IDEMPOTENCY:
   • Safe to rerun any phase multiple times
   • Won't create duplicates
   • Deduplication key: event_id for events, (farm, schedule, date) for MISSED

6. MERGE-ON-START LOGIC:
   • Prevents fragmentation of activities
   • Resumes ended instances if gap is small (3/5/12 min by type)
   • Different thresholds by activity type

7. SCHEDULE MATCHING:
   • When multiple schedules exist for same (farm, activity_type)
   • Uses scoring algorithm (weighted by start/end)
   • Picks schedule with best score (closest match)

📝 COMMON QUESTIONS & ANSWERS
================================================================================

Q: What are the valid status values?
A: IN_PROGRESS, EARLY, ON_TIME, LATE, MISSED (NOT COMPLETED!)

Q: When is status finalized?
A: In STEP-4 (Resolver), not in STEP-5 (Cron)

Q: Why does status remain IN_PROGRESS after aggregator?
A: Because schedule doesn't match until resolver runs in STEP-4

Q: What's the difference between started_offset and ended_offset?
A: started_offset = how early/late activity STARTED vs schedule
   ended_offset = how early/late activity ENDED vs ideal end

Q: What happens if duration > 3 hours?
A: Treated as anomaly, marked as LATE

Q: Why run phases in order 3 → 4 → 5?
A: Resolver needs ended instances from aggregator
   Cron needs resolved instances from resolver
   Wrong order causes missing/incomplete data

Q: Is MISSED detection working?
A: Currently disabled (can be re-enabled)

Q: What timezone should I use?
A: UTC for calculations, farm LOCAL for display

Q: How does schedule matching work?
A: Scoring algorithm with weighted offset comparison
   Start time 3x more important than end time

Q: What if multiple schedules exist?
A: Resolver picks the one with best score (lowest abs offset)

Q: Can I rerun phases safely?
A: Yes! All operations are idempotent

Code Files & Their Responsibilities:

edge_detector.py (Jetson)
  • Loads YOLO model
  • Processes video frames
  • Maintains state machine (INACTIVE → START/FRAME/END → INACTIVE)
  • Sends START_CANDIDATE, FRAME_AGGREGATE, END_CANDIDATE events

event_ingest_api.py (Backend, STEP 2)
  • Endpoint: POST /api/v1/ingest/event
  • Authenticates device via X-DEVICE-KEY
  • Validates event payload (timestamp, confidence, type)
  • Inserts into activity_detection_event (append-only)
  • OUTPUT: event logged with activity_instance_id = NULL

activity_aggregator.py (Backend, STEP 3)
  • Called by run_phase5.py
  • Processes: SELECT FROM activity_detection_event WHERE activity_instance_id IS NULL
  • START_CANDIDATE: Create or resume instance
  • FRAME_AGGREGATE: Update last_seen_at
  • END_CANDIDATE: Set actual_end_at, compute duration
  • OUTPUT: activity_instance (status = IN_PROGRESS)

activity_schedule_resolver.py (Backend, STEP 4) ⭐ CRITICAL
  • Called by run_phase5.py (AFTER aggregator)
  • Processes: Ended instances WHERE actual_end_at IS NOT NULL
  • Algorithm: Match to best schedule using scoring
  • Validates: Duration < 3 hours
  • Timezone: Converts UTC ↔ farm LOCAL
  • OUTPUT: Finalized status (EARLY/ON_TIME/LATE), schedule binding

missed_activity_cron.py (Backend, STEP 5)
  • Called by run_phase5.py (AFTER resolver)
  • Checks: For each schedule, did activity happen?
  • If not happened & window closed: Create MISSED instance
  • Currently disabled (can be re-enabled)
  • OUTPUT: MISSED instances only (if enabled)

run_phase5.py (Orchestrator)
  • Master controller
  • Runs: step3_aggregator() → step4_resolver() → step5_cron()
  • Guarantees correct order
  • Safe to call repeatedly
